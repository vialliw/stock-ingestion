Your BB question — confirmed verbatim
-------------------------------------
weekly_indicators is computed in rebuild_weekly_indicators (src/db.py):
  bb_mid    = AVG(Close)    OVER (PARTITION BY Ticker ORDER BY Date
              ROWS BETWEEN 19 PRECEDING AND CURRENT ROW)
  bb_std    = STDDEV(Close) OVER (same window)
  BB_Upper  = bb_mid + 2*bb_std;  BB_Lower = bb_mid - 2*bb_std;
  BB_Central = bb_mid
DuckDB STDDEV is STDDEV_SAMP (n-1). So: window 20, mult 2,
sample stddev, Close basis — matches your frozen spec; consume
BB_Upper/Central/Lower verbatim.

CAVEAT — no min-periods guard: the window is ROWS BETWEEN, not a
full-window requirement, so each ticker's first 19 weeks carry
partial-window bands (AVG over however many bars exist), NOT NULL.
If your spec requires strict 20-bar warmup, say so — a
CASE WHEN COUNT(*) OVER w = 20 THEN ... END guard is a one-line
change on our side; otherwise your bb_convention audit absorbs it.

Lock coupling — honest answer
-----------------------------
A CTAS is one atomic statement on the single RW conn — its read side
can't run on a snapshot cursor within the statement. But we can get
most of what you asked: implement create_as internally as
  SELECT on a snapshot cursor -> Arrow in-process
  -> CREATE OR REPLACE TABLE pivot.x AS SELECT * FROM arrow under
     _write_lock
so the lock is held only for the memory->table materialization, not
the 2.8M-row scan. bb_outcomes at ~15M thin rows stages fine (chunked
if needed); if it ever misbehaves it degrades to the plain lock-held
CTAS you already accepted. Worst-case stall becomes seconds, not the
scan duration.

Two decisions we need from you
------------------------------
1. PKs vs create_as. CREATE OR REPLACE TABLE ... AS SELECT infers the
   schema — PRIMARY KEY / NOT NULL constraints do NOT survive. Your
   DDL lists PKs; under pure CTAS rebuilds they'd be documentation
   only. Options:
   (a) constraint-free tables — your own duplicate_keys audit covers
       it; zero extra API surface.
   (b) add a `create_table` op driven by a STRUCTURED column spec —
       {columns:[{name,type,nullable,pk}]} as descriptor fields, still
       no SQL over the wire — then rebuilds run as `insert_select`
       into the pre-created constrained table. Real PK enforcement at
       write time; ~a day more work.
   Which do you want? (b) for PK-carrying tables + (a) CTAS elsewhere
   is a valid mix.

2. bb_outcomes r4_class: we recommend adding `value_text VARCHAR`
   rather than int-coding the category — self-describing at trivial
   cost. Confirm and we'll take that as the table shape.
